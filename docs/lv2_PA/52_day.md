## 1. 오늘 한 작업

### 1.1. Claude — 듀얼 OpenCR v4 전환 및 펌웨어 안전 정책 분석

#### 듀얼 OpenCR 프로토콜 및 시스템 구조 변경
- 기존 단일 OpenCR(v3) 구조를 바퀴 제어 보드와 로봇팔 제어 보드로 분리하는 듀얼 OpenCR(v4) 구조로 전환했습니다.
- CMD 및 STATE 프로토콜에 역할 바이트를 추가하여 프레임 크기를 각각 55 B와 192 B로 변경했습니다.
- 바퀴 제어를 기존 4륜에서 6륜(ID 1~6) 구성으로 변경했습니다.
- 호스트의 포트 설정을 단일 `/dev/opencr`에서 `ports=/dev/ttyACM0,/dev/ttyACM1` 방식으로 변경했습니다.
- STATE의 역할 값을 이용해 각 OpenCR 보드를 식별하도록 설계했습니다.
- 펌웨어, 호스트 인터페이스, 테스트, launch, udev, xacro 및 관련 문서를 수정했습니다.

#### 프로토콜 및 기존 코드 검증
- 프로토콜 v4의 필드 오프셋과 CRC-16/BUYPASS 테스트 벡터를 검증했습니다.
- 두 프로토콜 헤더 사본의 내용이 일치하는지 확인했습니다.
- 기존 C++ 테스트 9개를 `g++`로 별도 빌드하여 실행했으며 모두 통과했습니다.
  - Protocol 테스트: 5개
  - EstopLatch 테스트: 4개
- ROS 2 기반 루프백 테스트는 `hardware_interface` 의존성이 없어 실행하지 못했습니다.
- 프로토콜 필드, 상태 표현 및 오류 대응을 포함한 안전 정책과 기존 코드의 차이를 분석했습니다.

#### 펌웨어 안전 정책 분석
- 상태 머신, 오류별 대응 정책 및 향후 테스트 목록을 정리했습니다.
- 추가 결정이 필요한 항목 D1~D9를 도출했습니다.
- 다음 두 문서를 작성해 작업 인계 기반을 마련했습니다.
  - `CLAUDE.md`

## 2. 주요 발견 사항 및 안전 이슈

### 2.1. 우선 해결해야 할 펌웨어 문제

| 우선순위 | 발견 사항 | 위험 및 영향 |
|---|---|---|
| 높음 | ARM의 HOLD 상태가 유지되지 않음 | CMD 수신 후 의도치 않게 이동이 재개될 수 있음 |
| 높음 | OpenCR 부팅 시 `torqueOff` 실행 | 보드 리셋 시 로봇팔의 토크가 꺼져 자세를 유지하지 못할 수 있음 |
| 높음 | 호스트 `on_activate`에서 토크 OFF 프레임 전송 | 호스트 재시작 또는 재활성화 시 로봇팔 토크가 꺼질 수 있음 |
| 높음 | CMD 입력값 검증 부족 | 범위 초과, Inf 및 NaN 입력이 안전하지 않은 처리 경로로 이어질 수 있음 |
| 높음 | 모터 HW 오류 감지 로직 문제 | 실제 모터 오류를 잘못 판단할 가능성이 있음 |
| 높음 | SyncRead에서 누락된 모터의 이전 위치값 사용 | 오래된 상태값을 정상 측정값으로 오인할 수 있음 |

**중요:** 로봇팔의 HOLD 및 토크 유지 정책은 실제 하중이 걸린 상태에서 낙하 위험과 직결됩니다. 소프트웨어 변경만으로 안전성이 확보됐다고 판단하지 않고, 실제 하중 조건에서 별도 검증해야 합니다.

### 2.2. 프로토콜 및 제어 정책 관련 이슈
- 현재 v4 프로토콜로는 재활성화 절차와 HOLD/FAULT 상태를 충분히 표현할 수 없어 프로토콜 확장 또는 v5 전환 여부를 결정해야 합니다.
- 설정에 `ESTOP_PIN_ENABLE 1`이 남아 있습니다. 확정된 정책은 물리 E-stop을 사용하지 않는 것이므로 설정과 실제 코드의 일치 여부를 검토해야 합니다.
- diff_drive의 속도 한계가 펌웨어의 바퀴별 한계보다 높습니다. 단순히 범위 초과 명령을 거부하면 회전하면서 주행하는 일부 명령까지 거부될 수 있으므로, 상위 제어와 펌웨어의 제한 정책을 함께 조정해야 합니다.
- v3와 v4는 호환되지 않으므로 기존 펌웨어 및 호스트와의 혼용 가능성을 고려해야 합니다.

### 3.1. 환경 확인 결과

- Claude 작업 당시 머신은 Jetson이 아닌 x86 노트북이었으며 OpenCR이 연결되어 있지 않았습니다.
- 해당 환경에는 Arduino 도구와 `ros2_control` 의존성이 준비되어 있지 않았습니다.
- Codex 작업에서는 Jetson과 OpenCR 2대가 연결되어 있고 SSH 접속까지 준비된 상태라고 기록했습니다.
- ROS 2 host 빌드는 `/opt/ros/lyrical`의 `hardware_interface` 부재로 구성 단계에서 중단됐습니다.
