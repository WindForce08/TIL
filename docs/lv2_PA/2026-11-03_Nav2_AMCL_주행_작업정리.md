## 3. 개념 정리

### 3.1 Nav2 가 필요로 하는 것

Nav2 는 두 가지만 있으면 된다: **지도** (어디가 벽인가) + **지도 위 로봇 위치** (`map → odom` TF).

| 방법 | 하는 일 | 언제 |
|---|---|---|
| SLAM (slam_toolbox · cuVSLAM 등) | 달리면서 지도를 **만들고** 위치도 냄 | 지도가 없는 곳 |
| 정해진 지도 + AMCL | 있는 지도 위에서 위치만 **찾음** | 지도를 미리 아는 곳 |

→ Nav2 를 쓴다고 SLAM 을 꼭 같이 할 필요는 없다.

### 3.2 AMCL 이란

Adaptive Monte Carlo Localization = **있는 지도 위에서 라이다로 "지금 어디 있나" 를 찾는 방법** (Nav2 의 `nav2_amcl`).

비유: 눈을 가리고 아는 방에 들어감 → 후보 위치를 여러 개 떠올림 → 걸은 만큼 후보도 옮김 (= odom) → 손으로 벽을 더듬어 (= 라이다) 지도와 맞는 후보만 남김 → 반복하면 한 곳으로 모임.

```
후보 수백 개 (입자) = "로봇이 여기 · 이 방향일지도"
  ① 이동: odom 만큼 모든 후보를 옮김 (+ 오차만큼 흔듦)
  ② 비교: 각 후보 자리에서 "지도라면 라이다가 이렇게 보였을 것" vs 실제 /scan
  ③ 점수: 잘 맞는 후보에 높은 점수
  ④ 다시 뽑기: 점수 높은 후보 위주로 → ①
```

- Adaptive: 위치가 확실하면 후보 수를 줄이고, 불확실하면 늘림.
- RViz 에서 화살표 구름 (particle cloud) 으로 보이고, 잘 찾을수록 작게 모임.

| 입력 | 출력 |
|---|---|
| 지도 (`/map_amcl`) | **`map → odom` TF** (odom 이 쌓은 오차를 지도 기준으로 바로잡는 값) |
| 라이다 `/scan` | `/amcl_pose` (위치 + 확실한 정도 = 공분산) |
| odom (`odom → base_link`, EKF) | 입자 구름 |
| 처음 위치 (출발 자세) | |

- **왜 `map → odom` 인가**: odom 은 짧게는 부드럽고 정확하지만 오래 가면 틀어짐. AMCL 은 그 틀어진 만큼만 가끔 바로잡음. 로봇 위치 = `map → odom` + `odom → base_link`.
- 약점: 처음 위치를 정확히 줘야 함 · odom 이 나쁘면 못 따라감 · 빨리 돌면 흔들림 (두 라이다 합친 스캔이 회전 중 어긋남).

### 3.4 경기에 SLAM 을 쓰면 생기는 문제

- **좌표가 어긋남**: SLAM 지도 원점 = 켠 자리 → 계획기 좌표 (경기장 좌표) 로 바꾸는 단계가 따로 필요 (`mission_table.yaml` 의 `home [0,0,0]` 이 그 흔적).
- **박스가 지도에 안 나옴**: 70 mm 박스는 라이다 높이 (82 mm) 보다 낮음 → 어차피 도면 정보가 필요.
- **미로가 거의 대칭** (추정): 반복되는 기둥 격자를 SLAM 이 다른 칸과 잘못 맞출 위험. `amcl.yaml` 도 같은 이유로 전역 위치 찾기를 꺼 둠.

### 3.5 SLAM 이 쓸모 있는 때: 실물 경기장 확인용

실물 경기장이 도면과 다를 수 있음 (벽판 설치 오차). 처음에 **한 번** SLAM 으로 지도를 떠서 도면 지도와 겹쳐 본다.
- 잘 맞으면 → 그대로 AMCL.
- 많이 다르면 → 도면 지도를 고치거나, SLAM 지도를 경기장 좌표에 맞춰 AMCL 지도로 씀.

즉 SLAM 은 "지도 점검 도구", 경기 중 주행은 AMCL.

### 3.6 cuVSLAM (팀이 쓰려는 것)

- **우리 환경에서 돌아감**: Isaac ROS 5.0 (2026-09-21) 부터 ROS 2 Lyrical + JetPack 7.2 지원 (우리 Jetson = JetPack 7.2.1 · Lyrical). 패키지 이름이 `isaac_ros_visual_slam` → **`isaac_ros_cuvslam`**.
- ★ 지원 목록은 "Jetson Orin" 만 있고 Orin Nano 는 따로 없음 → 카메라 2 대 + 인식 (TensorRT) 과 같이 돌릴 GPU 여유는 실물에서 확인.
- 저장소에는 아직 cuVSLAM 설정이 없음.

| | cuVSLAM |
|---|---|
| 해 줌 | 카메라로 위치 추정: `odom → base_link` (시각 odom), `map → odom` (자체 SLAM), 지도 저장 · 불러오기 · 그 지도에서 위치 찾기 (`visual_slam/save_map` · `load_map` · `localize_in_map`) |
| 안 해 줌 | **Nav2 용 점유 지도 (occupancy grid) 없음** → Nav2 는 여전히 `/map` (map_nav) 필요 |
| 안 해 줌 | **전역 위치 찾기 없음** → 시작 자세를 밖에서 알려 줘야 함 |

- 기본값이 `publish_map_to_odom_tf` · `publish_odom_to_base_tf` **둘 다 true** → EKF · AMCL 과 TF 가 겹치면 위치가 튐. TF 주인을 하나로.
- 쓰는 방식:

| | A. cuVSLAM = odom 보조 (**채택**) | B. cuVSLAM = 위치 추정 전부 |
|---|---|---|
| `odom → base_link` | EKF (바퀴 + IMU + cuVSLAM odom) | cuVSLAM |
| `map → odom` | AMCL (라이다 + 도면 지도) | cuVSLAM SLAM |
| 좋은 점 | 경기장 좌표 그대로, 라이다가 벽을 잘 봄, 제자리 회전 미끄럼을 카메라가 보완 | 한 시스템 |
| 위험 | 노드 하나 더 | 아래 위험이 위치에 그대로, 시작 자세 맞추기 필수 |

- 실물 확인 ★ (cuVSLAM 담당):
  - 카메라 설정 충돌: 지금 `sensors.launch.py` 는 D435 `infra1` · `infra2` 를 끄고 컬러 + 깊이만 씀. cuVSLAM 은 IR 두 장 (압축 없이, 30 Hz 이상, 동기) + **IR 프로젝터 끔** 필요 → 인식의 깊이 품질에 영향 → Perception 과 합의 (프로젝터 번갈아 켜기 · RGBD 모드 `tracking_mode 2` 는 후보, 미확인).
  - IMU: 저장소 기준 D435 (IMU 없음, D435i 가 있음). 쓰려면 OpenCR IMU 위치 관계 · 시간 맞춤 미확정.
  - 미로 환경 (추정): 민무늬 벽판 = 특징점 부족, 경기장 밖 사람 움직임, 반복 기둥 = 잘못된 루프 닫기.

```

/scan + /map_amcl ──► amcl ──► map → odom                         (localization.launch.py 에 있음)
/map (map_nav) ──► Nav2                                            ← 새로 만듦
   planner_server · controller_server · behavior_server (spin) · bt_navigator
   global costmap (/map + 라이다 + inflation) · local costmap (라이다 + inflation)
   → /cmd_vel_nav (TwistStamped) → twist_mux → /cmd_vel → diff_drive
```

### 4.2 약속표 (팀 합의 → `interfaces.md` · `frames_tf.md`)

| 항목 | 약속 (제안) |
|---|---|
| 좌표 | 원점 = 경기장 왼쪽 아래 기둥 중심, +X 오른쪽 · +Y 위, yaw 0 = +X. 출발 자세 (0.694, 0.95, π) |
| TF | `map → odom` = AMCL 만, `odom → base_link` = EKF 만. diff_drive (`enable_odom_tf: false`) · cuVSLAM 은 TF 안 냄 |
| 토픽 | `/map` = 주행용, `/map_amcl` = AMCL 용, `/scan` = 앞 · 뒤 합친 것 (base_link), `/odometry/filtered` |
| 차체 | B안: 앞 +0.1328 · 뒤 −0.2135 · 반폭 ±0.1676 (Nav2 footprint · 라이다 `self_box` · drive `front_offset` 모두) |
| 정확도 목표 | 위치 3 cm · 방향 2° 이내 (제안, 통로 한쪽 여유 7 ~ 8 cm 의 절반 이하) |
| 위치를 잃었을 때 | `/localization/status` (std_msgs/String) 뜻 · 그때 누가 멈추는지 |
| 회전 속도 | AMCL · 스캔 합치기가 버티는 만큼 Nav2 회전 한계를 낮춤 ★ |

### 4.3 twist_mux (`opencr_hardware/config/twist_mux.yaml`, `use_stamped: true`)

| 입력 | 토픽 | 우선순위 | 시간 제한 | 발행 |
|---|---|---|---|---|
| teleop | `cmd_vel_teleop` | 100 | 0.5 s | 조이스틱 |
| drive | `cmd_vel_drive` | 50 | 0.25 s | drive_node (align · skill) |
| nav | `cmd_vel_nav` | 10 | 0.5 s | **Nav2 (지금 없음)** |

## 5. 역할 경계와 혼자 할 때

### 5.1 `odom` 프레임에서 자르기

| | 나 | 위치 추정 쪽 (cuVSLAM 담당) |
|---|---|---|
| TF | `odom → base_link` (EKF), `map → odom` (AMCL) | 없음 |
| 맡는 것 | 바퀴 odom 보정 (펌웨어와 바로 연결), IMU, EKF, AMCL, Nav2, 주행 RL | cuVSLAM 설정 · 카메라 · 단독 시험 |
| 주고받기 | cuVSLAM odom 토픽을 받아 EKF 에 넣음 | odom 토픽 + 정확도 보고 |

- 문제 가르기: odom 이 흐르면 odom 쪽, map 위치가 튀면 AMCL 쪽.

### 5.2 인지 코드를 안 건드리고 혼자 가능한가 → AMCL 로 가면 가능

| 필요한 것 | 어디서 | 상태 |
|---|---|---|
| `/scan` (합친 것) | 인지 scan_merger | 있음, 그대로 씀 |
| `/scan_front` · `/scan_rear` | 라이다 드라이버 (bringup) | 있음 |
| 도면 지도 2 장 + AMCL 설정 | mission_planner | 있음 |
| 바퀴 odom · IMU | 펌웨어 · opencr_hardware | 내 영역 |
| EKF 설정 | `bringup/config/ekf.yaml` | 있음, 보정만 |
| Nav2 설정 · launch | 없음 | **새 패키지 = 내 파일** |

- cuVSLAM 은 D435 설정 (IR 켜기 · 프로젝터 끄기) 이 인식 깊이에 영향 → 혼자 못 정함 → 나중에 odom 보조로.
- 주의: AMCL 값은 `mission_planner` 패키지 파일 → 작성자와 맞추거나 내 패키지에 사본. bringup 통합은 통합 쪽 파일 → 처음엔 내 launch 따로.

### 5.3 다른 팀에 부탁 (코드는 내가 안 고침)

| cuVSLAM 카메라 설정 합의 | Perception · cuVSLAM 담당 | 깊이 영상 영향 | AMCL 만으로 진행 |
| 위치 추정 = AMCL 로 문서 정리 | 통합 · Perception | `frames_tf.md` · `interfaces.md` 는 slam_toolbox, `puck_survey.yaml` 은 `mission_map` (Cartographer, 발행자 없음) | - |

## 6. 전체 작업 프로세스

```
[나]          0 합의·설치 ─┬─► 1 Nav2 뼈대 (장치 없이) ─────────────────┐
                          └─► 2 odom 보정 (실물) ─► 3 AMCL ─► 4 Nav2 실물 ─► 5 주행만 미션 ─► 6 전체 미션
[Perception]  self_box · udev ──(2 전에)──┘                                            ▲
[cuVSLAM]     카메라 합의 ─► 단독 시험 ─► odom 토픽 ─► 7 내 EKF 에 합침 (4 이후 아무 때나)  │
[팔]          그리퍼 · 집기 · 놓기 ────────────────────────────────────────────────────┘
```

| 단계 | 할 일 | 끝 기준 |
|---|---|---|
| 0 합의 · 준비 | 위치 기준 = AMCL, cuVSLAM = odom 보조, 좌표 · B안 · TF 주인표 문서화. 설치 승인 (이 PC · Jetson: nav2 · robot_localization, Jetson: coin_d4_driver). 5.3 부탁 전달 | 팀 승인 |
| 1 Nav2 뼈대 [PC] | 새 패키지에 Nav2 설정 · launch. 고정 `map → odom` + `backend:=mock` | 대기 자세 몇 곳으로 경로가 나오고 따라감 |
| 2 odom 보정 [실물] | `WHEEL_DIR`, 증속벨트/직결 확정, 직진 1 m · 제자리 한 바퀴로 바퀴 간격 · 미끄럼 보정, IMU 부호 · 바이어스, EKF 공분산 | 직진 · 회전 오차를 숫자로 앎 (예: 1 m 에 1 cm) |
| 3 AMCL [실물] | 출발 자세에서 스캔을 도면 지도에 겹쳐 봄, 조이스틱으로 한 바퀴 돌며 바닥 표시점에서 오차 측정, 잡음값 조정, `/localization/status` | 위치 3 cm · 방향 2° (제안) |
| 4 Nav2 실물 | 저속 대기 자세 1 곳 → 통로 · 회전 → `approach_poses.yaml` ok 자세 전부. 장애물 잠금 vs 회복 동작 확인 | 벽 접촉 없이 전부 도착 |
| 5 주행만 미션 | bringup 에 계획 모드 · planner_node · 위치 추정 · Nav2. 계획 순서대로 대기 자세 돌고 복귀 (drive_node `/drive/navigate`) | goto 전부 성공, 복귀 후 3 s 정지 |
| 6 전체 미션 | 팔 · 인식 합치기: 박스 1 → 장소 1 → 전체 | 완주 |
| 7 cuVSLAM (선택) | cuVSLAM odom 을 EKF 에 추가, 있음/없음 비교 | 좋아지면 켜 둠 |
| 병행: 주행 RL | 5 뒤 Nav2 추종기 자리에 PPO 를 넣어 같은 시험으로 비교 (2.4) | Nav2 보다 나으면 교체 |

- 순서를 지킬 것: odom → 위치 추정 → Nav2. 위치가 틀린 채로 Nav2 를 맞추면 원인을 못 가름.
- 위치 추정과 Nav2 문제의 절반은 odom 에서 온다 → 2 단계를 탄탄히.

### 7.4 Nav2 작업 목차

[PC] = 장치 없이 · [실물] = 로봇 필요 · ★ = 실측

0. **시작 전**
   - 0.1 이슈 #31 확인: `drive.yaml` 주석 "인지 Nav2 설정 0.025, 이슈 #31" → 저장소 밖 Nav2 설정이 있을 수 있음, 재사용 여부 결정
   - 0.2 설치 승인: nav2 (planner · controller · behaviors · bt_navigator · costmap_2d · smac_planner · mppi_controller · lifecycle_manager · map_server · amcl · collision_monitor), robot_localization
   - 0.3 약속 확정 (4.2)
1. **패키지 뼈대** [PC]: 새 패키지 (예: `navigation`) `config/` · `launch/` · `behavior_trees/` · `test/`, `nav2_params.yaml`, `navigation.launch.py` (`use_sim_time` · `params_file`, lifecycle 관리자는 위치 추정과 따로)
2. **입력 확인**: TF `map → odom → base_link → laser_*`, `/map` QoS transient_local, 라이다 (`/scan` 또는 `/scan_front` · `/scan_rear`), `/odometry/filtered`
3. **costmap**
   - 3.1 footprint B안 사각형, 주행 자세 팔이 그 안인지 ★
   - 3.2 global: static (`/map`) + obstacle (라이다) + inflation
   - 3.3 local: 로봇 중심 2 ~ 3 m 창, 0.025 칸, obstacle + inflation
   - 3.4 inflation ≤ 0.1 m (통로 약 0.70 m, 제자리 회전 반경 0.27 m → 한쪽 여유 7 ~ 8 cm) ★
   - 3.5 박스 · 받침대는 라이다에 안 보임 → static 층 (도면) 에만 의존
4. **경로 계획** (planner_server): Smac 2D (제자리 회전 가능), 기준선 NavFn, 모르는 칸 통과 금지, mission_planner A* 비용과 실제 경로 길이 비교
5. **경로 추종** (controller_server)
   - 5.1 MPPI (DiffDrive 모델), 비교안 Regulated Pure Pursuit + 제자리 회전
   - 5.2 속도: diff_drive 한계 (0.34 · 2.0 · 1.5) 아래, 회전은 AMCL 이 버티는 만큼 ★
   - 5.3 도착: `xy_goal_tolerance` 0.025 (drive_node `navigate.xy_goal_tolerance` 와 같게), 방향 허용오차 ★
   - 5.4 progress checker (좁은 곳 멈춤 판정)
   - 5.5 출력 `/cmd_vel_nav` TwistStamped
6. **회복 동작** (behavior_server): spin (drive_node 가 목표 0.025 m 안이면 spin 을 부름, 필수), backup · wait · costmap 지우기, 장애물 잠금과 충돌 확인 [실물]
7. **행동 트리** (bt_navigator): 기본 `navigate_to_pose` 로 시작 → 좁은 미로에 맞게 재계획 주기 · 회복 횟수 조정
8. **안전**: twist_mux 우선순위 확인, collision_monitor (선택, twist_mux 주석이 "nav 체인 마지막 = collision_monitor" 를 가정), **물리 비상정지 없음** 을 시험 절차에 반영
9. **drive_node · mission 연결**: 액션 이름 `navigate_to_pose` · `spin`, `front_offset` B안, Nav2 는 대기 자세까지 → align 이 이어받음, bringup 통합 (통합 쪽과)
10. **시험**: [PC] 고정 TF + mock → [PC] ok 대기 자세 전부 경로 계획만 → [실물] 바퀴 띄워 방향 확인 → 저속 1 곳 → 통로 · 회전 → 전체. 지표 = 성공률 · 벽까지 최소 여유 · 시간 · 도착 오차
11. **정리**: 실측값 · 근거 기록, README, `interfaces.md` · `frames_tf.md` 갱신 (팀 승인)

## 9. 주의

- **물리 비상정지 버튼 없음** - 조이스틱 정지 버튼 (소프트웨어) 뿐. 첫 주행은 바퀴를 띄워서, 다음은 아주 낮은 속도로, 사람이 전원 옆에.
- 실물 시험 (2 ~ 4 단계) 은 단계마다 범위를 정하고 진행.
- 설치 (nav2 · robot_localization · 드라이버) 는 승인 받고.
- 다른 팀 파일 (perception, mission_planner, bringup, control) 은 직접 고치지 않고 부탁 · 합의.
