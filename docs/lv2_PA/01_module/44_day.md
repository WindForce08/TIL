## 특정 브랜치만 클론하기 (`-b` 사용)

저장소를 복제할 때 `-b`로 브랜치를 지정하고, `--single-branch`를 붙이면 해당 브랜치만 가져온다.

```bash
git clone -b <브랜치명> --single-branch <저장소_URL>
```

예를 들어 `develop` 브랜치만 복제하려면 다음과 같이 실행한다.

```bash
git clone -b develop --single-branch https://github.com/사용자명/저장소명.git
```

최신 커밋만 가져와 다운로드 용량을 줄이려면 `--depth 1`도 추가한다.

```bash
git clone -b develop --single-branch --depth 1 <저장소_URL>
```

## 2. RealSense 객체 추적 시스템 실습

### 2.1. 객체 추적 시스템 실행

RealSense Tracking 관련 저장소를 클론하고 추적 시스템을 실행했다. RViz2를 이용해 카메라 영상과 객체 인식 결과를 시각적으로 확인했다.

**확인한 화면**

- Raw Image: RealSense 카메라의 원본 컬러 영상
- Mask: HSV 색상 범위에 따라 추출한 객체 영역
- Detection Overlay: 원본 영상에 객체 검출 결과를 표시한 화면
- Aligned Depth: 컬러 영상의 좌표에 맞춰 정렬한 깊이 영상

이를 통해 카메라에서 입력된 영상이 객체 검출 과정을 거쳐 시각화되는 흐름을 확인했다.

### 2.2. ROS 2 Topic 확인

ROS 2에서 각 노드가 데이터를 주고받는 통로인 Topic을 확인했다.

| Topic                            | Message Type                     | 역할                   |
| -------------------------------- | -------------------------------- | -------------------- |
| `/camera/camera/color/image_raw` | `sensor_msgs/msg/Image`          | 카메라 원본 컬러 영상         |
| `/perception/mask`               | `sensor_msgs/msg/Image`          | 색상 조건으로 추출한 마스크 영상   |
| `/perception/debug_image`        | `sensor_msgs/msg/Image`          | 객체 검출 결과를 표시한 디버그 영상 |
| `/target`                        | `geometry_msgs/msg/PointStamped` | 추적 대상의 위치 정보         |

**배운 내용**

- `sensor_msgs/msg/Image`는 ROS 2에서 영상 데이터를 전달할 때 사용하는 메시지 타입이다.
- `geometry_msgs/msg/PointStamped`는 3차원 점 좌표와 해당 좌표의 기준 프레임 및 시간 정보를 함께 전달하는 메시지 타입이다.
- Topic 이름을 확인하는 것만으로는 충분하지 않으며, Message Type과 실제 전달되는 데이터까지 확인해야 한다.

### 2.3. 객체 위치 데이터 확인

`/target` 토픽을 확인해 객체의 위치 좌표가 실제로 발행되는 것을 확인했다.

확인된 좌표 예시:

```
x = 0.1976
y = 0.2309
z = 0.03254
```

이 값은 객체 추적 노드가 발행한 위치 데이터다. 다만 좌표가 의미하는 방향과 단위는 메시지의 `header.frame_id` 및 노드의 좌표 변환 로직을 함께 확인해야 정확하게 해석할 수 있다.

**핵심 학습:** 객체를 영상에서 검출하는 것과 검출한 객체의 위치를 다른 ROS 2 노드가 사용할 수 있도록 전달하는 것은 별개의 과정이다.

## 3. ROS 2 Parameter 분석

### 3.1. 노드 파라미터 확인

다음 명령어를 사용해 `perception_node`의 설정값을 확인했다.

```
ros2 param dump /perception_node
```

주요 파라미터는 다음과 같다.

| 파라미터                  | 값                 | 의미                         |
| --------------------- | ----------------- | -------------------------- |
| `hsv_lower`           | `[93, 120, 35]`   | HSV 색상 필터의 하한              |
| `hsv_upper`           | `[130, 255, 255]` | HSV 색상 필터의 상한              |
| `min_area_ratio`      | `0.002`           | 작은 검출 영역을 제외하기 위한 최소 면적 비율 |
| `publish_debug_image` | `true`            | 디버그 영상 발행 활성화              |

### 3.2. HSV 색상 필터 이해

HSV는 색상을 색조(Hue), 채도(Saturation), 명도(Value)로 표현하는 색상 모델이다.

- **H (Hue):** 어떤 색상인지 구분한다.
- **S (Saturation):** 색상이 얼마나 선명한지 나타낸다.
- **V (Value):** 색상이 얼마나 밝은지 나타낸다.

`hsv_lower`와 `hsv_upper`는 검출할 색상의 범위를 설정한다. 카메라 영상에서 이 범위에 해당하는 픽셀을 추출하면 객체 후보 영역을 만들 수 있다.

`min_area_ratio`는 너무 작은 영역이 객체로 검출되는 것을 줄이기 위한 설정이다. 값이 너무 크면 실제 작은 객체까지 제외될 수 있다.

### 3.3. 파라미터와 코드의 관계

파라미터는 프로그램을 수정하지 않고도 실행 시 동작을 조정할 수 있도록 하는 설정값이다.

예를 들어 HSV 범위를 조절하면 검출할 색상을 바꿀 수 있고, 디버그 영상 발행 여부를 변경하면 시각화용 데이터의 발행을 제어할 수 있다.

이를 통해 ROS 2 노드의 동작을 이해할 때는 소스 코드뿐 아니라 실제 실행 중인 파라미터도 함께 확인해야 한다는 점을 배웠다.

## 4. 오늘의 실습 실행 흐름

오늘 확인한 인지 시스템의 데이터 흐름은 다음과 같다.

```
RealSense D435
      |
      v
원본 컬러 영상 + Depth 영상
      |
      v
ROS 2 카메라 토픽
      |
      v
Perception Node
      |
      +----> Mask 영상
      |
      +----> Detection Overlay
      |
      +----> /target 좌표
                    |
                    v
             후속 제어 노드
```

이 구조에서 인지 노드는 카메라 데이터를 받아 객체를 검출하고 위치 정보를 발행한다. 제어 노드는 이 위치 정보를 입력으로 사용해 로봇의 움직임을 결정할 수 있다.

단, 실제 제어 노드가 `/target`을 구독하고 정상적으로 동작하는지는 별도의 통합 테스트가 필요하다.

## 6. SSH 및 Git 문제 해결 과정

### 6.1. SSH 연결 오류

SSH 접속 과정에서 다음 오류를 확인했다.

```
client_loop: send disconnect: Broken pipe
ssh: connect to host 192.168.50.2 port 22: No route to host
```

두 오류는 의미가 다르다.

- `Broken pipe`: 기존 SSH 연결이 끊어졌다는 의미다.
- `No route to host`: 대상 장비까지 네트워크 경로를 확보하지 못했다는 의미다.

SSH 접속에 실패했다고 해서 반드시 SSH 서버 자체가 문제인 것은 아니다. 네트워크 인터페이스, IP 주소, 라우팅, 케이블 연결 상태 등을 구분해 확인해야 한다.

### 6.2. Git Push 거부

Git 저장소에 Push를 시도했을 때 다음 오류가 발생했다.

```
! [rejected] main -> main (non-fast-forward)
```

이 오류는 원격 브랜치에 로컬 브랜치에는 없는 커밋이 존재해, 현재 상태 그대로는 Push할 수 없다는 의미다.

일반적인 해결 순서는 다음과 같다.

1. `git status`로 작업 트리 상태를 확인한다.
2. `git fetch origin`으로 원격 저장소의 최신 정보를 가져온다.
3. 로컬과 원격의 커밋 차이를 확인한다.
4. 필요한 변경 사항을 통합한 뒤 Push한다.

원격 저장소의 변경 사항을 확인하지 않고 강제 Push를 실행하면 다른 작업자의 커밋을 덮어쓸 수 있으므로 주의해야 한다.
